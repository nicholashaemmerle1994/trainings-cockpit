# TB-23 / P3–P4 — Vorlage speichern und verwenden

**Stand:** 11.11.2026 · **Branch:** `feature/tb-23-trainingsplaner-erweiterung`
**Umfang:** Oberfläche für lokale Workout-Vorlagen. Kein Remote-Write.

## 1. „Als Vorlage speichern“ (P3)

- Aktion im bestehenden `PlanSheet` unterhalb der Berechtigungen, vor
  „Einheit löschen“.
- Nur bei einer **gespeicherten** geplanten Einheit aktiv. Während eines
  lokalen Entwurfs ist der Knopf gesperrt; der Hinweis sagt, dass eine Vorlage
  den zuletzt gespeicherten Stand übernehmen würde.
- Kleines zweites Blatt (`TemplateSaveSheet`) über dem PlanSheet:
  Name vorausgefüllt, 1–120 Zeichen, keine Zeilenumbrüche/Tabulatoren,
  Sportart und Aufbau sind read-only.
- Doppelklick-Schutz über einen Ref; der Knopf ist während des Requests
  gesperrt.
- Erfolg nennt den Vorlagennamen und stellt klar, dass kein Training an
  intervals.icu gesendet wurde.
- Fehler zeigen den stabilen Grund aus `TemplateError`/`CloneError`
  verständlich an. `serialization_failed` erklärt die Grenze des vorhandenen
  Speicherwegs, statt den Aufbau zu kürzen.

Es wird ausschließlich `POST /api/planner/templates/from-plan/{event_id}`
aufgerufen. Der Body enthält nur `name`; die Quelle ist die persistierte
`event`-Zeile.

## 2. „Aus Vorlage erstellen“ (P4)

- Dezente Aktion oben im bestehenden `AddWorkoutSheet`; darunter bleibt die
  bisherige Neuanlage mit Sportart-Dropdown, Name und den drei Startformen.
- Die Vorlagenliste wird erst beim Öffnen geladen. Sie zeigt Name, Sportart,
  Dauer, Distanz und Abschnittszahl, optional mit lokaler Suche.
- Ein Klick ruft `POST /api/planner/templates/{id}/project` mit einer neuen
  `draft_id` und dem gewählten Tag auf. Die Antwort enthält frische Knoten-IDs.
- Der vollständige Aufbau wird als `nodes` an `NewPlanConfig` übergeben und im
  vorhandenen `PlanSheet` über `POST /api/planner/draft/new` projiziert.
- Kein Event-Create beim Öffnen, Auswählen oder Projizieren. Erst der
  bestätigte Speichern-Knopf im Editor nutzt den vorhandenen
  `POST /api/planner/draft/save`-Pfad.
- Jede Verwendung erzeugt eine neue `draft:new:…`-ID; dieselbe Vorlage bleibt
  unverändert und ist beliebig oft verwendbar.
- Der lokale Entwurfsspeicher merkt sich den Vorlagenaufbau (`new_plan.nodes`),
  damit ein wiederhergestellter Entwurf nicht auf die Standard-Startform
  zurückfällt.

## 3. Zustände und Fehler

| Situation | Anzeige |
|---|---|
| Vorlagenliste lädt | „Vorlagen werden geladen…“ |
| Keine Vorlage | ruhiger Leerzustand mit Verweis auf „Als Vorlage speichern“ |
| Suche ohne Treffer | „Keine Vorlage passt zu …“ |
| Beschädigte Vorlage | Eintrag deaktiviert, Grund `corrupt` verständlich |
| Projektion schlägt fehl | Fehlertext im Vorlagenblatt, erneuter Versuch möglich |
| Netzwerkfehler | konkreter Fehler; kein automatischer Create |
| Offline | Vorlagen-Speichern und Kopieren sind gesperrt bzw. erklärt |

## 4. Tests und Prüfung

Automatisiert:

- Backend-Vorlagenvertrag aus P1/P2 (`tests/test_planner_templates*.py`).
- Frontend: `npm run build` (TypeScript + Vite) fehlerfrei.
- Manuell mit kontrollierten lokalen Fixtures geprüft: Vorlage speichern,
  Erfolgszustand, Vorlagenliste, Suche, Projektion in den Editor, neuer
  Entwurf mit erhaltenem 45-min-Aufbau. Keine intervals.icu-Verbindung.

## 5. Bekannte Grenzen

- Der bestehende Serializer lehnt Schrittnamen mit Maßangabe ab; eine solche
  Planung lässt sich nicht als Vorlage speichern. Die UI erklärt den Grund.
- Vorlagen speichern keine Uhrzeit (D-94/P1-Vertrag).
- Es gibt in P3/P4 bewusst keine Kategorien, Tags, Pflichtfelder oder eigene
  Vorlagen-Seite.
