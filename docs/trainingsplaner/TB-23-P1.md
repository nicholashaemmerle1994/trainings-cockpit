**Stand:** 11.11.2026 · **Branch:** `feature/tb-23-trainingsplaner-erweiterung`

## 1. Umfang

P1 legt ausschließlich die lokale Grundlage für Workout-Vorlagen:

- neue SQLite-Tabelle `workout_template`,
- kanonischer Knoten-Import/-Export über den bestehenden Codec aus
  `planner/operations.py`,
- tiefer Klon mit neuen Knoten-, Plan-, Entwurfs- und Vorgangs-IDs,
- Ablehnung nicht sicher schreibbarer Strukturen über die vorhandene
  Serializer-Grenze `prepare_write`,
- Scope über `account_id`/`athlete_id`,
- stabile, explizite Fehlercodes.

Nicht Teil von P1: HTTP-Endpunkte, Vorlagenliste im Browser, „Als Vorlage
speichern“, Vorlagenauswahl beim Tages-Plus, Wochenkopie und Copy-Jobs.

## 3. Schema

```sql
CREATE TABLE IF NOT EXISTS workout_template (
    template_id     TEXT PRIMARY KEY,
    account_id      TEXT NOT NULL,
    athlete_id      TEXT NOT NULL,
    name            TEXT NOT NULL,
    sport           TEXT NOT NULL,
    schema_version  INTEGER NOT NULL,
    nodes_json      TEXT NOT NULL,
    created_at      TEXT NOT NULL,
    updated_at      TEXT NOT NULL,
    source_event_id TEXT
);
CREATE INDEX IF NOT EXISTS idx_workout_template_scope
    ON workout_template(account_id, athlete_id, updated_at);
```

Kein Foreign Key auf `event`: Eine Vorlage überlebt das Löschen der
Quellplanung. `schema_version` ist die Vorlagen-Inhaltsversion (aktuell `1`),
keine Datenbank-Migration. Die Tabelle wird über das vorhandene
`CREATE TABLE IF NOT EXISTS` idempotent ergänzt; `init_db` bleibt unverändert.

## 4. Kanonische Knoten

`nodes_to_json(nodes)` und `nodes_from_json(raw)` sind öffentliche Wrapper um
den bestehenden Codec in `operations.py`. Die gespeicherte Form entspricht der
Vorgangs-/Planform (`id`, `kind`, `end`, `target`, `children`, …), nicht der
API-Detailform (`node_id`). Es gibt kein drittes Knotenformat.

Beim Klonen werden `notes` und `source_ref` auf `null` gesetzt. Echte Notizen
und ursprüngliche Quellreferenzen werden nicht übernommen; Plannotizen und
Schrittnotizen werden vorher abgelehnt.

Beim Lesen prüft `_row_to_template()` mehr als JSON und Deserialisierbarkeit:
Der Knotenbaum wird über denselben Klon-/Serializer-Weg wie beim Speichern
validiert. Doppelte Node-IDs, leere oder offene Strukturen, unbekannte
Inhalte, nicht unterstützte Sportarten und ein leerer Name gelten als
`corrupt`. `get_template()` gibt solche Zeilen nicht als gültig zurück;
`list_templates()` zeigt sie mit `available=False` und
`error_code="corrupt"`.

## 5. Fehlercodes

### `CloneCode`

`empty_structure`, `notes`, `unsupported_node`, `nested_repeat`,
`skip_final_recovery`, `absolute_hr`, `power_zone`, `open_end`,
`empty_repeat`, `invalid_date`, `invalid_time_zone`, `invalid_identity`,
`serialization_failed`.

### `TemplateCode`

`name_empty`, `name_too_long`, `name_invalid`, `invalid_scope`,
`scope_mismatch`, `sport_unsupported`, `source_not_cloneable`,
`schema_unsupported`, `corrupt`, `not_found`.

`TemplateError` trägt bei einem Klonfehler zusätzlich `clone_code` mit dem
spezifischen `CloneCode`. Die Codes hängen nicht vom Wortlaut einer
`SerializationError`-Meldung ab: bekannte Fälle werden am Modell geprüft,
alles Übrige endet stabil als `serialization_failed`.

## 6. Schnittstellen

```python
save_from_plan(conn, plan, *, name, account_id, athlete_id,
               source_event_id=None, now=None) -> WorkoutTemplate
list_templates(conn, *, account_id, athlete_id) -> list[TemplateSummary]
get_template(conn, template_id, *, account_id, athlete_id) -> WorkoutTemplate | None
delete_template(conn, template_id, *, account_id, athlete_id) -> bool
instantiate(template, *, target_date, time_zone, draft_id=None,
            account_id, athlete_id) -> tuple[PlannedWorkout, WorkoutDraft]
clone_for_new_plan(source, *, target_date, time_zone, account_id, athlete_id,
                   keep_time=False, draft_id=None, local_id=None,
                   operation_id=None) -> tuple[PlannedWorkout, WorkoutDraft]
```

`list_templates` liefert nur Metadaten und Summen, keine Knoten. Defekte oder
fremdversionierte Zeilen bleiben mit `available=False` und `error_code`
sichtbar, statt die ganze Liste zu verhindern.

`instantiate` vergleicht `template.account_id`/`template.athlete_id` mit dem
übergebenen Kontext und bricht bei Abweichung mit `scope_mismatch` ab, bevor
ein Plan oder Entwurf entsteht.

## 7. Sicherheitsgrenzen

- Kein Netzwerkzugriff in `clone.py` und `templates.py`.
- Keine Schreibe in `event`, `activity` oder `planner_operation`.
- `prepare_write` bleibt die einzige Fähigkeitsgrenze; P1 baut keinen zweiten
  Serializer und keine zweite Workout-Textsyntax.
- `get_template` validiert den gespeicherten Knotenbaum, bevor er als gültig
  zurückgegeben wird; `list_templates` markiert beschädigte Zeilen als
  `corrupt`.
- `instantiate` prüft den Account-/Athleten-Scope der Vorlage gegen den
  Aufrufer und liefert bei Abweichung keinen Entwurf.
- Vorlagen sind lokale Snapshots; sie erzeugen weder ein intervals-Event noch
  eine intervals-Vorlagenbibliothek.
- `source_event_id` ist nur Herkunft, keine aktive Remote-Referenz.

## 9. Verbleibende Grenzen / P2

- Es gibt noch **keine API**; P2 muss die Event-Zeile über einen öffentlichen
  Leser in ein `PlannedWorkout` überführen (heute ist `_event_from_row` privat).
- Es gibt **keine UI**; P3/P4 folgen.
- Es gibt **keine Copy-Job-Tabellen** und keine Wochenkopie; P5–P7 folgen.
- Vorlagen werden nur für `Run`/`Ride`/`Swim` angeboten. Andere Sportarten
  werden abgelehnt, weil der bestehende Anlegefluss nur diese drei kennt.
- Vorlagen speichern keine Uhrzeit; Wochenkopien sollen die Uhrzeit später
  behalten.
- Der bestehende Serializer lehnt Schrittnamen mit einer Maßangabe ab (z. B.
  „100 m“), weil der Workoutparser sie als Feld lesen würde. Eine Vorlage aus
  einer solchen Planung wird mit `serialization_failed` abgelehnt, nicht
  gekürzt; eine Schwimmstruktur mit neutralen Schrittnamen klont regelkonform.
- Archivierte Quell-Events sind lokal nicht sicher erkennbar; P5 muss die
  Restgrenze dokumentieren und die `coverage`-Prüfung erzwingen.
- Ein echter intervals-Live-Test ist nicht Teil von P1.
